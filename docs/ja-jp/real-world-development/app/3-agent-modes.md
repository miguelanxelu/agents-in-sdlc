最初に、小さな機能をプロジェクトに追加しました。より大規模な変更には、さらに確実なプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業できるように設計されており、必要なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを実践します。issue を起点に新機能を作り、コードの妥当性と機能の動作を確認して、最終的にプロジェクトへマージします。

> [!NOTE]
> 機能開発を続ける間、同じセッションを使います。通常はファイル種別に応じて異なるセッションや PR を使いますが、ここでは主な概念に集中するため手順を簡略化します。

このレッスンでは、次の作業を行います。

- GitHub issue から新しいエージェントセッションを開始します。
- **Plan** モードで要件を決めます。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動検証します。

機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズして、MCP による検証を追加し、QA エージェントを作成して機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、訪問者がカテゴリや発行元でゲームを絞り込める必要があります。バックログの issue には機能が記載されていますが、カテゴリを組み合わせる方法など、コーディング前に合意が必要な詳細があります。Plan モードで決定事項を整理してから、範囲を限定した実装を Autopilot に任せます。

## 背景

AI コーディングエージェントを開発フローに導入しても、基本的な手順は変わりません。むしろ、これまで以上に重要になります。多くの開発者は、次のような流れで作業します。

1. 実施内容が詳しく書かれた issue を開きます。
2. 実装内容の計画を立てます。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードレビューと継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れを調整したものになります。

標準的な手順に沿うことで、AI が生成したコードが要件を満たし、手作業で書いたコードと同じレビューを受けるようにできます。

## セッションモード

**セッションモード**は、エージェントにどの程度の自律性を与えるかを決めます。プロンプトフィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。変更案を確認し、次に進む前に入力できます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが自律的に作業し、入力を待たずにコードを書き、テストを実行して反復します。

Plan モードで開始して計画をレビューし、その後 Autopilot で実装します。

## issue からセッションを開始する

開始する前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** の下にある Tailspin Toys のリポジトリフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これはテンプレートに含まれる issue なので、新たに作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

   ![GitHub Copilot app の issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. issue がセッションに添付されていることを確認し、モード選択メニューで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションで動作しない場合は、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチを確認できます。issue から開始したため、Copilot は機能リクエストをすでにコンテキストとして持っています。次のプロンプトを送信します。

```plaintext
この機能を実装してください。
```

Copilot の質問に回答し、計画を issue の受け入れ条件に照らし合わせます。カテゴリと発行元による絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認します。複数カテゴリの組み合わせ方や、一致するゲームがない場合の動作など、不明確な点について話し合います。

計画には、プロジェクトの既存ツールを使った lint、ユニットテスト、E2E テスト、型チェックを含めます。フィルター機能の実装とテストに範囲を絞り、品質改善のワークフローを終えるまで PR は作成しません。計画を承認する前に修正を依頼します。後で検証できるよう、issue の URL と合意した追加条件を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンに表示される同等のオプションを選択します。承認するとモードも切り替わると決めつけず、モード表示が **Autopilot** になっていることを確認してください。

Copilot が実装を始めます。計画に沿ってコードを生成し、テストを実行しながら作業を反復します。

> [!NOTE]
> 承認すると実装がすぐに始まる場合があります。先に計画をレビューしてください。依存関係の不足やポート競合が報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。自分で起動したサーバーだけを停止してください。

## 実装をレビューして検証する

生成されたコードは、他のコードと同じようにマージ前にレビューします。コードを確認し、サイトを実行して問題がないことを検証します。

1. **Changes** を開き、フィルターの実装とテストを確認します。
2. 複数カテゴリや発行元の組み合わせも含め、結果を issue と承認した追加条件に照らし合わせます。変更が既存のリポジトリの指示に従っていることも確認します。
3. lint、ユニットテスト、E2E テスト、型チェックの結果を調べます。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、影響するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカルサーバーを再利用できます。以前のレッスンではなく、この worktree のサーバーがテストに使われていることを確認します。

## 新機能を試す

コードに問題がないように見えても、実際に動くか確認します。Copilot にアプリを起動させ、ブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザーキャンバスで開くよう Copilot に依頼します。

   ```plaintext
   アプリを起動し、ブラウザーキャンバスで開いてください。
   ```

2. アプリが起動し、Copilot app 内にブラウザーウィンドウが開くまで待ちます。
3. カテゴリを選択し、表示される結果がカテゴリに一致することを確認します。フィルターを解除し、発行元を選んで結果を確認します。
4. カテゴリと発行元のフィルターを組み合わせ、issue と承認済みの計画に照らして結果を確認します。複数カテゴリを使える場合は、合意した組み合わせの動作も検証します。
5. 結果に該当するゲームがない条件を試し、空の状態を確認します。フィルターを解除またはリセットし、一覧全体が戻ることを確認します。
6. 確認が終わったら、次のプロンプトで、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

   ```plaintext
   開発サーバーを停止し、ブラウザーキャンバスを閉じてください。
   ```

## 次のレッスンのためにセッションを保持する

フィルター機能の PR は、まだ作成したりマージしたりしないでください。レッスン 4 から 8 まで、同じセッション、worktree、ブランチを使います。次はフィルターのコードにカスタム指示を適用し、スキルと QA の改善を追加してから、レッスン 8 で変更をまとめて PR を作成し、マージします。開発サーバーを停止した後、セッションをそのままにしておき、次のレッスンで再開します。

## まとめと次のステップ

さまざまなエージェントモードを使って機能を構築し、レビューしました。このレッスンでは、次の作業を行いました。

- GitHub issue から新しいエージェントセッションを開始しました。
- **Plan** モードで要件を決めました。
- **Autopilot** モードで新機能を実装しました。
- コードをレビューしました。
- ブラウザーキャンバスで機能を手動検証しました。
